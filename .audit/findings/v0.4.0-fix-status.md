### Evaluated and rejected as contract bugs

- **`installModule(replayable=true, ...)` cross-chain replay** — chain-agnostic property is the documented purpose of `_hashTypedDataSansChainId`. For `Kernel7702`, the same replayable signature being usable on every chain where the EOA has activated 7702 is the intended mathematical consequence of opting into `replayable=true`. UI/UX issue, not a contract flaw.
- **Enable-mode install non-atomic with the executing userOp** — `_install(sig.packages)` commits during validation phase; if execution reverts, install persists. Owner explicitly authorized the install via the install digest, separately from the userOp action. Owner can uninstall later.
- **`KernelImmutableECDSA._initialize` does not call `_setRoot`** — the docstring explicitly documents this; parallel authorities are an opt-in feature of the deployment-time package list, not a hidden backdoor.

## Per-finding review (UNFIXED items)

### H-01 — Phantom session key (enable-mode ERC-1271) (was #3)

- **Where:** `src/core/ModuleManager.sol:138-152` (enable branch in `_erc1271IsValidSignatureNowCalldata`); `:362-375` (`_verifyInstallSignatureRaw` digest computed only over `(INSTALL_PACKAGES_STRUCT_HASH, nonce, installHash(packages))`, NOT over the ERC-1271 `hash`); `:341-354` (`_checkNonce` is view-only).
- **Confirmed by:** static read + dynamic — `test/audit/PhantomSessionKey.t.sol` two PoCs both PASS on v0.4.0 (kernel returns `ERC1271_MAGICVALUE` for an attacker-chosen hash).
- **Severity rationale:** the owner's pre-signed install package is an INTENT to install K, not CONSENT to arbitrary pre-install ERC-1271 authority for K — the contract conflates the two. Once the enable signature exists, the kernel will validate K's signatures over arbitrary hashes (Permit2 digests, Seaport orders, Uniswap-X / CowSwap orders, EIP-712 messages) for as long as the install nonce remains unconsumed. K does not need to be "compromised" in the traditional sense — session keys legitimately sign 1271 hashes during normal use; an attacker who has the leaked enable signature plus K's normal-life signatures can wrap them through this path. Direct theft via order-protocol flows; **HIGH** for "direct theft of funds with conditions".
- **Failing test:** `test/audit-pending/PhantomSessionKey.t.sol` — two assertions, both fail on v0.4.0 with `0x1626ba7e... != 0xffffffff...`.
- **Suggested fix:** bind the enable-mode digest to the ERC-1271 `hash` argument (e.g., a separate `INSTALL_PACKAGES_FOR_ERC1271_HASH` struct hash that includes `hash`). A view-only nonce on the ERC-1271 path is OK if the hash is bound, because each (nonce, packages, hash) triple authorizes exactly one signature.

### H-02 — WeightedECDSASigner split-sig: bundler-as-guardian gas-drain

- **Where:** `kernel-7579-plugins/src/signers/WeightedECDSASigner.sol:179-187` — `proposalHash = keccak256(PROPOSAL_TYPEHASH, sender, id, callDataHash, nonce)`. **Excludes** `accountGasLimits`, `preVerificationGas`, `gasFees`, `paymasterAndData`. `:212-227` accumulates weight from proposalHash signers; `:229-252` recovers the last sig against `userOpHash` (which DOES include gas fields) and adds its weight unless the recovered signer is also one of the proposalHash signers.
- **Threat model:** one configured guardian's key is held by a bundler (or the bundler IS one of the guardians, which is common in self-bundled session-key flows). Honest guardians collect proposalHash signatures for the user's intended `(callData, nonce)`. The user submits a userOp with intended gas fields and a last-slot sig from a guardian over the user's `userOpHash`. The bundler intercepts, REWRITES the gas fields upward (within their own ceiling), RE-SIGNS the new `userOpHash` with their guardian key, drops it into the last slot, and submits through their own beneficiary. Because `proposalHash` is unaffected by gas changes, the honest proposal sigs remain valid; the modified userOpHash is signed by the bundler-guardian. Threshold met. EntryPoint reimburses inflated gas to the bundler-guardian's beneficiary, drained from the kernel's deposit.
- **Severity rationale:** direct theft of the kernel's EntryPoint deposit. The split-sig scheme intentionally excludes gas fields from `proposalHash` so honest guardians can pre-approve callData without committing to gas; that intent is supposed to be preserved by the last sig binding `userOpHash`. The bug is that the last-sig signer can be ANY one guardian who has weight — even one weighted below the threshold by themselves. A single colluding bundler-guardian breaks the gas-binding property. **HIGH** under "direct theft of funds requiring specific operational conditions".
- **Failing test:** not added in this commit. Outline: install signer with `[G_honest=1, G_bundler=1]` threshold 2; collect `sig0 = G_honest(proposalHash)` for an intended callData; have the bundler produce `sig1' = G_bundler(modifiedOpHash)` where `preVerificationGas` is inflated; submit through `bundler.beneficiary`; assert `entryPoint.balanceOf(kernel)` is decremented by the INFLATED gas amount, not the user's intended gas amount. Recommended for the team to add at fix time.
- **Suggested fix options:** (1) bind gas fields into `PROPOSAL_TYPEHASH` (loses the "pre-approve callData and let bundler set gas" UX); (2) require the LAST signer to ALSO appear in `proposalSigners` so a fresh guardian-signature alone cannot complete a userOp; (3) cap allowed gas inflation against a benchmark (hard to do generically).

### H-03 — `execute` selector grant → non-root validator becomes effective root

- **Where:** `src/Kernel.sol:160-174` — `_processUserOp` only checks the OUTER selector for non-root validators. When `_allowedSelector(V, Kernel.execute.selector) == true` and `vInfo[V].hook == HOOK_MODULE_INSTALLED_NO_HOOK`, the no-op gating branch is taken; the inner execution mode and target are NOT bound at validation time. `Kernel.execute(mode, executionData)` (`src/Kernel.sol:207-210`) only requires `_onlyEntryPointOrSelf()`. `_executeCall` (`src/core/ExecutionManager.sol:42-50`) does `_call(target, value, data)` (`:108-113`) — when `target == address(this)`, the inner call's `msg.sender == address(this)`, so `setRoot` / `installModule` / `setNonce` / `grantAccess` / `setValidNonceFrom` / `upgradeToAndCall` all accept the call.
- **Trace (verified by failing test):**
  1. Owner installs side-validator V (Alice's) with `internalData = abi.encodePacked(NO_HOOK, Kernel.execute.selector)`. Owner's mental model: "Alice can move my assets via `execute(target, value, data)`."
  2. Alice signs a userOp with `vType=VALIDATOR`, `vId=V`, and `callData = execute(SINGLE_MODE, abi.encodePacked(address(kernel), 0, abi.encodeWithSignature("installModule(uint256,address,bytes)", 1, aliceOwnValidator, ...)))`.
  3. Validation gating takes the no-op branch. V's signer signs userOpHash; validation passes.
  4. EntryPoint dispatches `kernel.execute(...)`. Auth passes (`msg.sender == EP`).
  5. `_executeCall` → `_call(target=address(this), 0, installModule(...))`. Inner call's `msg.sender == address(this)` ⇒ `installModule`'s `_onlyEntryPointOrSelf()` passes. Alice's validator is installed.
  6. Alice repeats with `data = setRoot(aliceVid)`. Root flips to Alice's validator. Owner is locked out.
- **Severity rationale:** direct privilege escalation / governance takeover. The owner DELIBERATELY granted `execute.selector`, but the contract's interpretation of that grant is much broader than typical owner mental models: granting `execute` is equivalent to granting **every** privileged self-call PLUS arbitrary external calls. There is no narrower way to express "V can call execute() to move my assets but cannot self-call into me". **HIGH**.
- **Failing test:** `test/audit-pending/ExecuteSelectorGrantTakeover.t.sol` — installs Alice's side validator with `execute.selector` granted, performs the install-then-setRoot self-call attack, asserts `kernel.root()` is unchanged. Currently FAILS on v0.4.0 because root flips to Alice's validator.
- **Suggested fix options:** (1) in `_executeCall` / `_executeBatchCall` / `_executeDelegateCall`, reject `target == address(this)` UNLESS the dispatching authority is the current root (track the calling vId via transient storage during validation); (2) at validation time, when the outer selector is `Kernel.execute.selector`, decode `executionData` enough to reject `target == address(this)` for non-root vIds; (3) at install time, disallow granting `Kernel.execute.selector` (and other dispatch selectors) to non-root vIds — require the owner to use `executeUserOp`'s wrapped path which DOES check the inner selector (`src/Kernel.sol:168-173`). Document strongly that granting `execute` is equivalent to granting root.

### H-04 — Installed executor → root takeover via `executeFromExecutor` self-call

- **Where:** `src/Kernel.sol:217-231` — `executeFromExecutor` and `_executeFromExecutor` are guarded only by the `executorHook` modifier (`src/core/ModuleManager.sol:56-62`). The modifier authenticates that the caller IS an installed executor; it does NOT constrain the inner dispatch target. `_execute` → `_executeCall` → `_call(target=address(this), ...)` produces the same self-call privilege escalation as H-03.
- **Trace (verified by failing test):**
  1. Owner installs an executor module M. Owner's mental model: "M can do its specific role (e.g. recurring payments) via `executeFromExecutor`, but it has no root authority."
  2. M (or any function callable on M) invokes `kernel.executeFromExecutor(SINGLE_MODE, abi.encodePacked(address(kernel), 0, abi.encodeCall(setRoot, attackerVid)))`.
  3. `executorHook` modifier: M is installed, hook check passes, no actual hook runs (NO_HOOK).
  4. `_execute` → `_executeCall` → `_call(target=kernel, 0, setRoot(attackerVid))`. Inner call's `msg.sender == address(this)`. `setRoot`'s `_onlyEntryPointOrSelf` passes. Root flips. Owner is locked out.
- **Severity rationale:** identical to H-03 but via the executor path. The owner trusted the executor for a SPECIFIC role; the contract silently grants it root takeover authority. A compromised or buggy executor takes over the kernel. **HIGH** (governance takeover, owner consent only to the executor role, not the root role).
- **Failing test:** `test/audit-pending/ExecutorSelfCallTakeover.t.sol`. Installs a `MaliciousExecutor` whose `takeoverViaSelfCall(kernel, innerCall)` calls `kernel.executeFromExecutor(SINGLE, encode(kernel, 0, innerCall))`. Currently FAILS on v0.4.0 because root flips after the takeover sequence.
- **Suggested fix:** the same fix as H-03 closes this — track the dispatching authority (validator vId for `execute`, executor address for `executeFromExecutor`) and reject `target == address(this)` unless that authority is the current root.

### M-01 — `vType=ROOT` skips the root validator's hook (was #4)

- **Where:** `src/Kernel.sol:161-174` — the first if-clause `vType == VALIDATION_TYPE_ROOT` short-circuits past `_setValidationHook(userOpHash, ...)`. `executeUserOp` then reads `_validationHook(userOpHash) == 0` and `_preHook(0, ...)` / `_postHook(0, ...)` (`src/core/HookManager.sol:53-66`) become no-ops.
- **Confirmed by:** static read + dynamic — `test/audit/RootHookBypass.t.sol::test_PoC_root_hook_is_bypassed` PASSES (preCalls/postCalls remain 0 despite a real hook being configured on the root validator's vInfo).
- **Severity rationale:** owner-configured hook silently fails to fire on root-signed userOps. The realistic threat model is a partially-compromised root (HSM breach, multisig seat takeover) where the hook was the defense-in-depth line. No direct theft on its own — root signer must already be compromised. **MEDIUM** for defense-in-depth bypass under privileged-compromise.
- **Failing test:** `test/audit-pending/RootHookBypass.t.sol` — asserts `preCalls == 1` and `postCalls == 1`. Currently fails with `0 != 1`.
- **Suggested fix:** resolve the effective vId (root fallback) before the gating block, then ALWAYS call `_setValidationHook(userOpHash, $.vInfo[resolvedVid].hook)`. The selector allowlist short-circuit can stay; the hook must wire through.

### M-02 — TimelockPolicy proposal contents not signer-bound (was #6)

- **Where:** `kernel-7579-plugins/src/policies/TimelockPolicy.sol:196-235` — `_handleProposalCreationInternal` reads `proposalCallData` and `proposalNonce` directly out of the policy-slot signature. The signer's authorization is over `userOpHash`, which excludes `userOp.signature` bytes.
- **Severity rationale:** the bundler/MITM can queue an arbitrary proposal but cannot execute it without the signer separately authorizing a userOp with the matching `(callData, nonce)`. Practical impact is griefing — bundler burns the user's nonce queueing a useless proposal instead of the user's intended one — plus a trust-break between the signer's audit log and on-chain state. **MEDIUM** griefing.
- **Failing test:** `kernel-7579-plugins/test/audit-pending/TimelockProposalNotSignerBound.t.sol`. Submits two no-op userOps with byte-identical fields except the signature slot, observes that `userOpHash` is the same for both, asserts the user-intended proposal is queued. Currently fails with `0 != 1`. Test scope is policy-level unit harness against `MockTimelockAccount`; an end-to-end integration test through a real kernel + permission install (TimelockPolicy + ECDSASigner) is recommended at fix time.
- **Suggested fix:** include `keccak256(userOp.signature)` (or the policy slot bytes) in the digest the signer signs, OR have the policy read the proposal contents from a fixed-position field that is signed over by the signer.

### M-03 — Lib4337 `checkValidation` is hardcoded to timestamp mode

- **Where:** `src/lib/Lib4337.sol:34-40`:
  ```solidity
  function checkValidation(uint256 validationData) internal view returns (bool) {
      (uint48 vAfter, uint48 vUntil, address res) = parseValidationData(validationData);
      if (vAfter > block.timestamp || vUntil < block.timestamp) {
          return false;
      }
      return res == address(0);
  }
  ```
  EntryPoint v0.9 supports a "block-mode" validation-data flag where `MODE_BIT = 0x800000000000` set on `validAfter` / `validUntil` indicates "these are block numbers, not timestamps". The kernel's `checkValidation` ignores the flag and unconditionally compares against `block.timestamp`.
- **Effect:** any validator that returns block-mode validation data (with `MODE_BIT` set on `validAfter`) makes `vAfter > block.timestamp` always true (since `MODE_BIT ≈ 1.4e14`, dwarfing any plausible block.timestamp), so `checkValidation` always returns false. This silently breaks `installModule(replayable, nonce, packages, signature)` (outer require fails → install always reverts) and the `_erc1271IsValidSignatureNowCalldata` enable-mode branch (short-circuits and returns false).
- **Severity rationale:** functionality break for users who configure block-mode validators. No direct theft; the module-install-via-signature path and the enable-mode 1271 path are silently disabled for those users. The current kernel-7579-plugins repo doesn't ship a block-mode validator (ECDSAValidator returns 0/1), so the in-tree blast radius is low. Externally-deployed validators that opted into block-mode would hit this. **MEDIUM** for "smart contract unable to operate".
- **Suggested fix:** parse `MODE_BIT` from `validAfter` / `validUntil` in `checkValidation` and compare against `block.number` instead of `block.timestamp` when the flag is set. Match EntryPoint v0.9 semantics.

### L-01 — TimelockPolicy premature `Executed` during validation (was #5)

- **Where:** `kernel-7579-plugins/src/policies/TimelockPolicy.sol:259` — `proposal.status = ProposalStatus.Executed` writes during `checkUserOpPolicy` (validation phase). EntryPoint v0.9 catches execution-phase reverts (`innerHandleOp`) but commits validation-phase state.
- **Severity rationale:** the AA nonce is consumed post-validation by `EntryPoint.sol:835`, so the same `(callData, nonce)` could never be retried even if the status weren't burned. The user can always pick a fresh nonce. Real impact is "state record claims execution happened when it didn't" + griefing potential for emergency timelock-gated actions. **LOW**.
- **Failing test:** `kernel-7579-plugins/test/audit-pending/TimelockPrematureExecuted.t.sol` — asserts `status == Pending` after the execution phase reverts. Currently fails with `2 != 1` (Executed=2, expected Pending=1).
- **Suggested fix:** move the status write into a post-execution path (executor-hook callback or a designated sentinel transition). Alternatively, add a separate `Attempted` state.

### L-02 — `_verifyStatelessSignature` PERMISSION pseudo-policy match — partial fix (was #8)

- **Where:** `src/core/ModuleManager.sol:411-432` — the LAST package matched by `pId` is now required to be `MODULE_TYPE_SIGNER` (line 415-416). Earlier-position packages are NOT type-checked against `MODULE_TYPE_POLICY`; they're just expected to implement `IStatelessValidatorWithSender`. If a non-policy package (type 3 selector / type 4 hook / type 1 validator / type 7 stateless) happens to implement `validateSignatureWithDataWithSender` and returns `true`, it gets to vote on the permission's signature chain.
- **Severity rationale:** the owner had to sign an `Install[]` whose non-policy module returns true unconditionally — narrow admin misconfiguration + an attacker-authored module. **LOW** under the precondition rule.
- **No failing test added** — the partial fix already constrains the most realistic exploit shape (the signer slot). Tightening the gate to also require non-last positions to be `MODULE_TYPE_POLICY` is a defensive hardening; the team can add a unit test alongside.

### L-03 — `_intersectValidationData` `_usesBlockNumberFormat` mis-classifies `validUntil = 0`

- **Where:** `src/lib/Lib4337.sol:71-73`:
  ```solidity
  function _usesBlockNumberFormat(uint48 validAfter, uint48 validUntil) internal pure returns (bool) {
      return (validAfter & MODE_BIT != 0) && (validUntil & MODE_BIT != 0);
  }
  ```
  `_intersectValidationData` uses `_usesBlockNumberFormat` to detect block-mode, then `require(preUsesBlock == resUsesBlock, ValidityFormatMismatch())`.
- **Effect:** a validator that returns "block-mode start, no expiry" (`validAfter` has `MODE_BIT`, `validUntil = 0`) is mis-classified as timestamp-mode, because `validUntil & MODE_BIT == 0`. Intersecting it with another block-mode validation data reverts.
- **Severity rationale:** narrow corner case — only a block-mode validator that uses `validUntil = 0` to mean "no expiry" hits this. Functional break, not theft. **LOW**.
- **Suggested fix:** treat `validUntil = 0` as "no expiry" before the format check; decide block-mode purely from `validAfter`'s `MODE_BIT`.

### I-01 — Type-10 stateless validator drops `sender` (was #9)

- **Where:** `kernel-7579-plugins/src/validators/ECDSAValidator.sol:84-99`, `signers/ECDSASigner.sol:53-69`, `signers/WeightedECDSASigner.sol:111-128` — each function carries an explicit NatSpec block stating the `sender` parameter is intentionally unused, with a recommendation to pair with `CallerPolicy` if sender restriction is needed.
- **Severity rationale:** the documented intent removes the implicit-guarantee aspect — type 10 here means "stateless validator that can be called via the sender-aware ABI but doesn't gate on it". Demoted to **INFO**.
- **Suggested follow-up:** if the team wants the type-10 advertisement to be load-bearing in audit-tooling terms, drop the type-10 claim from `isModuleType` rather than documenting it away.

## Other observations (no severity)

- **`grantAccess` semantics are REPLACE, not APPEND.** `_grantAccess(vId, selectors)` always increments `vInfo[vId].nonce` and maps the new `selectors` to the new nonce; previously-granted selectors at the OLD nonce silently no longer match. So `grantAccess(V, [s1])` followed by `grantAccess(V, [s2])` leaves V with ONLY `s2` (s1 is implicitly revoked). This is a side effect of the same nonce-bump that closed the selector-resurrect bug (F-02) — the REPLACE semantics are required to invalidate stale grants on reinstall. The natspec ("Grants a validation access to specific function selectors") doesn't communicate the REPLACE behaviour. Owner can recover by re-calling with the full list. Suggested fix: clarify natspec to "**Replaces** the validation's allowed-selector set" and consider an additional `extendAccess` function.
- The selector dispatch (`Kernel._fallback`, `SelectorManager.sol`) lets `hook = HOOK_MODULE_INSTALLED_NO_HOOK` ⇒ open access for ANY caller (not just EntryPoint). Documented in `SelectorManager.sol:50` (`address(0) = entryPoint-only`, `address(1) = anyone`). Owner responsibility — but worth noting in user-facing docs that `hook=address(1)` on a fallback selector is "publicly callable".
- The fallback path is OUTSIDE the `validateUserOp` flow, so the validation hook + selector allowlist do NOT apply. By design, but worth documenting in the kernel security model so users know that fallback selectors bypass owner-configured rate-limit/validation-hook protections.
- `ValidationManager._uninstallPolicyWithVid` (`src/core/ValidationManager.sol:218-221`) accesses `$.policies[$.policies.length - 1]` inside `unchecked`. With `policies.length == 0`, the subtraction underflows in `unchecked` but Solidity 0.8.30's array bounds check still reverts with `Panic 0x32` rather than the custom `InvalidPermissionUninstallOrder` error. Cosmetic, no security impact.

## Fixed on v0.4.0

These items from `nemesis-report.md` are confirmed fixed on `origin/v0.4.0`. Each was verified statically (re-reading via `git show origin/v0.4.0:<path>`) and dynamically (the original PoCs at `test/audit/*.t.sol` — which previously passed on master — now revert with `AA23` on v0.4.0).

The team applied a single conceptual change — "always advance `nonce` on `_initializeValidation`" — that simultaneously closed the default-allow bug (F-01), the selector-resurrect bug for the validator path (F-02), and the same bug for the permission-signer path. The codeless-validator drain (F-03) was closed by switching from low-level `.call` to a typed interface call so Solidity's `extcodesize` check now happens for free on the authorization path. `_setRoot(ValidationId)` (F-04) was closed by adding the installed-vId check.

### F-01 — Default-allow selector grant — FIXED ✓ (was #1)

- **Where:** `src/core/ValidationManager.sol:_initializeValidation` line 121 — the empty-internalData branch now does `++$.vInfo[vId].nonce;`.
- **Why this fix works:** with the default `allowed[vId][sel] = 0` and post-install `nonce = 1`, `_allowedSelector(vId, anySel)` returns `false` until the owner calls `grantAccess`. The non-empty install path also flows through `_grantAccess` which bumps `nonce`, so a validator installed with `internalData = abi.encodePacked(hook, sel)` only authorizes the signaled selector(s).
- **Confirmed by:** `test/audit/DefaultAllowSelector.t.sol` — both PoCs (`test_PoC_side_validator_can_takeover_via_setRoot`, `test_PoC_side_validator_directly_calls_execute`) revert `AA23` on v0.4.0; previously drained funds and flipped root on master.

### F-02 — Selector grants resurrect on reinstall — FIXED ✓ (both paths) (was #2)

- **Where:** same nonce-bump as F-01. `_uninstallValidation` only zeroes `hook` (`src/core/ValidationManager.sol:195`), but the next `_initializeValidation` requires `hook == HOOK_MODULE_NOT_INSTALLED` and bumps `nonce`, so any stale `allowed[vId][sel] = N` no longer matches the post-reinstall `nonce = N+1`.
- **Confirmed by:** `test/audit/SelectorResurrect.t.sol` and `test/audit/PermissionSelectorResurrect.t.sol` — both PoCs revert `AA23` on v0.4.0; previously passed the resurrected grant.

### F-03 — Codeless-address validator drains — FIXED ✓ (was #7)

- **Where:** `src/core/ValidationManager.sol:_validateUserOpValidator` (line 364-373) and `_verifySignature` (line 286-303) both use a typed interface call (`validator.validateUserOp(op, opHash)` / `validator.isValidSignatureWithSender(...)`). Solidity's high-level external call includes an `extcodesize` check, so a codeless validator now reverts the userOp/1271 verification rather than returning a fake-success.
- **Confirmed by:** `test/audit/EmptyValidator.t.sol::test_PoC_codeless_validator_authorizes_any_signature` reverts `AA23` on v0.4.0; previously passed.
- **Note:** the install path (`ModuleManager._install` line 272) still uses a low-level call without an `extcodesize` guard, so a codeless module install silently succeeds. The next validation attempt reverts (safe-fail), so this is no longer a security bypass — just a footgun. An `extcodesize` check at install time would be a quality-of-life improvement.

### F-04 — `_setRoot(ValidationId)` missing installed-vId check — FIXED ✓ (was #10)

- **Where:** `src/core/ValidationManager.sol:441-443` — `_setRoot(ValidationId vId)` now requires `$.vInfo[vId].hook > HOOK_MODULE_NOT_INSTALLED` for non-zero vIds (with the explicit fallback exception for zero-vId).
